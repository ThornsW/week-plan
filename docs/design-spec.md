# week-plan 设计规格

本文件是 2026-08-24 一次完整设计讨论的产物，记录 35 个已确认的决定及其理由。它是实现的依据；实现与本文冲突时，先改本文再改代码。

标注 `【假设】` 的条目是讨论中未明确覆盖、由实现方按既定原则推定的细节，可随时推翻。

---

## 1. 项目定位

一个部署在个人博客服务器上的**周计划表**，以 WordPress 插件形式存在，只在 wp-admin 后台使用，单用户。

它取代旧的 Memo 桌面应用，但不是它的新版本：无共享代码、无数据迁移、不同运行形态。旧仓库 `Project_Library/Memo` 冻结不动，退场时机由用户自行处理。

核心工作流：每周花一小段时间，把待办从侧栏拖进下一周的具体某天；平时打开看本周该做什么，做完打勾。

## 3. 领域概念

- **待办（todo）**：一件要做的事。有标题、Markdown 笔记、优先级、截止日、标签、子任务。可以是一次性的，也可以是长期的（例如一项持续三个月的学习计划）。
- **排期（schedule）**：一条"某待办 × 某一天"的记录。一个待办可以有任意多条排期，日期不必连续。这是本项目和普通待办清单的根本区别。
- **未排期**：没有任何排期记录的待办，堆在侧栏底部的折叠区，称为"未来计划"。
- **单天完成**：某一条排期被打勾，表示"这一天那份做完了"。
- **最终完成**：整个待办结束。与单天完成互相独立——可以提前结项，也可以排期全做完但待办仍未结项。

## 4. 数据模型

### 4.1 待办：借用 WordPress 内容类型

注册自定义内容类型 `weekplan_todo`，`public => false`、`show_ui => false`、`exclude_from_search => true`。

这样做的收益：白拿 WordPress 的标签系统、回收站、权限和数据关联，不必自己写标签的增删改。
`public => false` 同时保证待办没有前台链接，不会被搜索引擎收录，也不会出现在博客后台的文章列表里。

| 字段 | 存放位置 |
|---|---|
| 标题 | `post_title` |
| Markdown 笔记原文 | `post_content`（原样存 Markdown，不经 WordPress 编辑器） |
| 创建/更新时间 | `post_date` / `post_modified` |
| 优先级 | meta `_weekplan_priority`，整数 0=低 / 1=中 / 2=高 |
| 截止日 | meta `_weekplan_due_date`，`YYYY-MM-DD` 或空 |
| 最终完成 | meta `_weekplan_done`，0/1 |
| 最终完成时间 | meta `_weekplan_done_at` |
| 子任务 | meta `_weekplan_subtasks`，JSON 数组 `[{text, done}]` 【假设】 |

子任务用 JSON 而非单独建表：每个待办通常只有几条，永远整体读写，不需要单独查询。

### 4.2 标签：自有分类

注册分类法 `weekplan_tag`，挂在 `weekplan_todo` 上。

**必须是自己的分类，不能复用博客文章的标签**，否则待办标签会混进博客的标签云并出现在公开页面上。

标签颜色存为 term meta `_weekplan_color`，沿用旧 Memo 的默认值 `#7AA2F7`。

### 4.3 排期：自建表

排期是几千行的热数据，且需要按日期区间查询，塞进 WordPress 的附属表（键值结构、值字段无索引）会让"查这一周"既慢又难写。因此单独建表。

```sql
CREATE TABLE {$wpdb->prefix}weekplan_schedule (
  id        BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  todo_id   BIGINT UNSIGNED NOT NULL,
  plan_date DATE            NOT NULL,
  done      TINYINT(1)      NOT NULL DEFAULT 0,
  done_at   DATETIME        NULL,
  position  INT             NOT NULL DEFAULT 0,
  PRIMARY KEY  (id),
  UNIQUE KEY uniq_todo_date (todo_id, plan_date),
  KEY idx_date (plan_date),
  KEY idx_todo (todo_id)
) {$charset_collate};
```

- `UNIQUE (todo_id, plan_date)` 保证一个待办在同一天最多占一格。
- `position` 支持同一天内手动排序。
- 用 `dbDelta()` 建表并处理后续升级。dbDelta 对 SQL 格式挑剔：字段名与类型之间两个空格、用 `KEY` 而非 `INDEX`、`PRIMARY KEY` 后两个空格，写错会导致每次加载都重复执行 ALTER。
- 待办被删除时级联清理对应排期（WordPress 不管自建表，需在 `before_delete_post` 钩子里自己删）。

### 4.4 数据迁移

**不迁移。** 旧 Memo 的 SQLite 数据全部作废，新库从空开始。

## 5. 界面

位置：wp-admin 后台自定义页面，访问权限 `manage_options`。

选后台不选前台的理由：日程表需要整屏宽度和三栏布局，放在博客前台会被主题的正文容器限宽（`bangumi-list` 已经踩过这个坑，当时不得不写破格样式冲破 argon 的 `.post-content`）；后台页面是空白画布，主题在那里没有影响力，而且天生在登录之后。

### 5.1 三栏布局

```
┌──────────────┬─────────────────────────┬──────────────┐
│ 待办清单     │ 本周（纵向 7 个日期组） │ 详情         │
│              │                         │              │
│ [逾期 · 3]   │  周一 8/24  ← 今天      │ 标题         │
│              │   ▸ 卡片                │ 笔记(MD)     │
│ 待办 A       │   ▸ 卡片                │ 截止日       │
│  已完成 5 天 │  周二 8/25              │ 优先级       │
│ 待办 B       │   ▸ 卡片                │ 标签         │
│  已完成 12天 │  周三 8/26              │ 子任务       │
│              │  ...                    │ 已完成 12 天 │
│ ▾ 未来计划(7)│  周日 8/30              │              │
└──────────────┴─────────────────────────┴──────────────┘
```

**左栏 · 待办清单**：以**待办**为单位（不是以天为单位），每条显示标题、标签色点、"已完成 N 天"。这一栏同时承担"长期规划全貌"和"待排期池"两个职责。已排期的待办按最近一次排期日期排序；完全未排期的收进底部可折叠的"未来计划"分组，按截止日排序。

**中栏 · 本周**：纵向排列 7 个日期分组，每组标题是"周X · M/D"，下面竖着列该天的卡片。

选纵向分组而非横向 7 列看板的理由：横向 7 列在常见窗口宽度下每列只有百来像素，放不下"标题 + 标签 + 状态"的卡片；纵向分组在同样空间里能舒服地看到 3-4 天，且拖拽是垂直方向的，符合列表直觉。代价是"一眼看完一周"的日历感弱一些。

**右栏 · 详情**：点击卡片或左栏条目后在此编辑。用常驻侧栏而非弹层，因为编辑和排期是交替进行的动作，弹层每次遮挡整个日程表会打断节奏。

### 5.2 周的定义与导航

- 自然周。起始日**复用 WordPress 内置的 `start_of_week` 选项**，不新增设置项。
- 有"上一周 / 下一周 / 回到本周"导航。
- 打开时默认显示**今天所在的这一周**，不是下周。
- **「规划下周」按钮**：一键跳到下周视图，同时展开左栏、按截止日排序，进入专注排期的状态。这是把"每周花一小段时间规划"这个仪式变成一个按钮，成本只有几十行。不做逐条询问的向导——那种流程用两次就会觉得烦。
- "今天"必须用站点时区计算（`wp_timezone()` / `current_time()`），不能用服务器 UTC 时间。

### 5.3 逾期区

左栏顶部一个默认折叠的"逾期"区，显示条数。

- 只汇总**上一周**的未完成排期，理解为"上周总结"。
- 更早的未完成排期**静默留在数据里**，永远保持未完成状态，不再提醒，翻页回去仍能看到真实历史。
- 逾期区只在查看"今天所在的这一周"时出现；翻到其它周时不显示。【假设】
- 本周内已经过去的天，其未完成卡片仍留在各自的日期分组里，不进逾期区。【假设】
- 系统**不会**自动把逾期任务滚动到今天——那会篡改"我原本计划哪天做"这个事实。

### 5.4 视觉状态

完成 = **点亮**，未完成 = **未点亮**。这与"完成即划掉变灰"的常规相反，更接近贡献热力图：一周做满了，整片是亮的。

实现方式：点亮 = 提高整张卡片的饱和度和不透明度；未点亮 = 低饱和、半透明。标签色在两种状态下都保持可见。**两种状态的对比度要拉高**，一眼可辨。

最终完成需要比单天完成更强的视觉信号（例如整张卡片加粗描边或打勾角标），避免两级完成状态混淆。

后台样式相当中性，不会干扰这套配色。

实测后调整过一次（2026-08-25）：对比度改成靠"有色 vs 无色"拉开，而不是明暗微差 —— 未完成卡片整体是灰白描边、左侧色带去饱和成灰，只有标签小签保留颜色；完成后整张卡片被标签色染上。这样一屏扫过去，做完了多少一眼可读。

### 5.4.1 字体

界面用博客的 **Maple Mono NF CN**，和站点视觉统一。

字体文件在 `wp-content/uploads/fonts/` 下（Regular 与 Bold 两个 woff2，共约 12 MB），是全站共享的，不属于任何主题。因此插件**只引用不打包**：生产环境上浏览器逛博客时早就缓存过了，仓库也不必背 12 MB 二进制。`@font-face` 由 PHP 检查文件存在后动态输出，文件不在就不输出，自动落回备用字体栈。

它是等宽字体，中文字身比例偏宽，所以行高统一给到 1.7 左右；好处是数字天然对齐成列，日号和"N 项"这类信息不需要额外对齐手段。

### 5.5 明确不做的功能

- **搜索**：删除。在日程表里"这件事在哪一天"本身就是答案，全文搜索没有位置。
- **手机端适配**：不做。因此可以放心使用浏览器原生拖拽 API——它在移动端不工作，而移动端不在范围内。
- **多用户**：不做，表里不预留 `user_id`。将来真需要时加迁移，比现在背着一个永远等于 1 的列划算。
- **时刻粒度**：不做。最小粒度是"一天"，没有开始时间和时长。
- **重复规则**：不做。长期计划靠"批量排期"一次性生成多条排期记录。

## 6. 交互

### 6.1 四种拖拽手势

| 手势 | 语义 |
|---|---|
| 左栏 → 某一天 | **新增**一条该天的排期；待办本身仍留在左栏 |
| 某一天 → 另一天 | **只移动被拖的这一天**，原来那天消失。不是整体平移 |
| 某一天 → 拖出中栏 | **删除**这一天的排期 |
| 同一天内上下拖 | 调整当天顺序（写 `position`） |

拖拽必须是所见即所得的单格操作。"整体顺延 N 天"放进右键菜单，绝不绑在拖拽上——否则一次误拖会打乱三个月的排期。

### 6.2 批量排期

一个对话框：选日期区间 + 勾选周几 → 一次生成多条排期记录。解决"接下来三个月每天做"无法手工拖 90 次的问题。

### 6.3 打勾

- 卡片上的勾 = 单天完成，写 `weekplan_schedule.done`。
- 详情栏里的"结项" = 最终完成，写 `_weekplan_done`。结项不影响已有排期记录。

### 6.4 进度显示

只显示**已完成天数**，如"已完成 12 天"，**不给分母**。因为计划总天数会随情况变化，分母看起来像承诺，实际随时会变，是误导。

## 7. 技术实现

- 后端：PHP，跟随线上环境（PHP 8.3）。
- 前端：wp-admin 页面内自写 HTML + CSS + 原生 JavaScript，使用浏览器原生 HTML5 拖拽 API。
- **无构建步骤**、无前端框架、无 npm。部署就是传文件；半年后回来改一行 HTML 不需要先修复依赖链。
- 数据交互走 WordPress 的 AJAX 端点（`wp_ajax_weekplan_*`），每个写操作校验 nonce 和 `manage_options` 权限。
- Markdown 渲染在服务端，用单文件的 Parsedown 1.8.0（原样放在 `plugin/week-plan/vendor/`），不引入构建链。它 2019 年后未再更新且历史上有 XSS 公告 —— 单用户、内容自己写，这条威胁不成立，但仍开了 `setSafeMode` 并叠一层 `wp_kses_post` 兜底。详见 `vendor/README.md`。

## 8. 部署

宿主环境（版本部分 2026-08-24 只读实测，其余见 `Project_Library/TX_VPS`）：腾讯云 CVM，OpenCloudOS 9.4，2 vCPU / **1.7 GiB 内存无 swap**，WordPress 7.0.2 + Nginx 1.28 + PHP-FPM 8.3.22 + MariaDB 10.6.20，宝塔面板管理，域名 `thornsw.cn`。

插件形态相对独立服务的收益，正是冲着这台机器的约束去的：

| 事项 | 插件方案 |
|---|---|
| 新增常驻进程 | 无（PHP-FPM 已在跑）。独立 Python 服务约需 +60~80 MB 常驻，在这台机器上不是小数 |
| 新增端口 / 安全组变更 | 无 |
| 新增域名 / 证书 | 无。现有证书是手动部署的非通配符证书，加子域名等于多一份季度续期家务 |
| 新增 Nginx vhost | 无。也不必绕开现有的 `00-catchall-redirect.conf` |
| 认证系统 | 无。复用 WordPress 登录、密码哈希、session、nonce |
| 备份 | 随现有 `wp db export` 一并覆盖 |

部署方式：把 `plugin/week-plan/` 整个目录 rsync 到 `wp-content/plugins/week-plan/`。

**已知代价**（明确接受，不打折）：

1. 待办数据与博客数据库焊死。博客出问题会波及一个和博客无关的私人工具；将来想拆成独立应用，需要写一次性导出脚本。
2. 本地开发需要一整套 WordPress。TX_VPS 的 AGENTS.md 里那条"本地插件版本不等于线上部署版本，发布前必须分别核对"同样适用于本项目。
3. 语言从 Python 变为 PHP，旧 Memo 的数据层代码也无法复用，真正从零开始。

线上写操作沿用 TX_VPS 项目的规矩：先备份、一次只做一个可验证的小变更、变更后写 ops 记录。

## 9. 本地开发环境

`dev/docker-compose.yml` 起一套 WordPress + MariaDB，版本对齐线上（WP 7.0.x、PHP 8.3、MariaDB 10.6）。
